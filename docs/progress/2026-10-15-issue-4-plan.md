## 完了範囲

pgxの接続pool、番号付きSQL migration、Workspaceを条件にする共通保存処理を実装する。業務serviceは同じtransaction内で自身のDomainテーブルを更新し、その確定内容を更新記録へ渡す。業務テーブルの全schema、Ory認証、投影Worker、同期transportは対象外。共有更新のHTTP試験には試験専用の業務テーブルと認可済み主体を使い、本番へ仮の認証やCRUD入口を公開しない。

| 条件 | 対象・期待結果                                                                            | 判定方法                                                                                                 |
| ---- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| AC-1 | 空DB、bootstrap時のDB、導入済みschemaで同じ初期schemaへ収束。再実行は保存済みデータを保つ | 実PostgreSQLのtable/constraintとmigration記録、保存済みfixtureを照合。失敗SQLではmigration全体がrollback |
| AC-2 | 業務更新、版、更新記録、操作結果が同時に確定                                              | 更新記録の保存をDB側で失敗させ、業務データ・版・記録・結果の件数を比較                                   |
| AC-3 | 同一操作は同一結果へ収束。同じ版への別更新は一つだけ採用                                  | 並列HTTP要求、応答喪失後の再送、内容を変えた操作ID、再起動後の照合                                       |
| AC-4 | 作成・更新・削除を、commit順の位置と版で再開読取できる                                    | 複数ページ、ページ間の追加更新、再起動、履歴欠落を実DBで照合                                             |
| AC-5 | 別WorkspaceのIDだけで保存・取得できない                                                   | 二つのWorkspaceの認可済み主体を使い、IDの差替えをHTTP/DBで拒否                                           |
| AC-6 | DB停止中の要求を成功へ補完しない。backupから状態・版・位置・再送結果を復元                | 管理対象の試験専用PostgreSQLで停止/再起動、pg_dump/pg_restoreを実行して比較                              |

## 実装と採用判断

共通の版と更新位置はopaqueな文字列にする。Workspaceの更新行をtransaction内でロックし、内部の連番がcommit順と一致するようにする。更新位置は各イベントのランダムな安定IDとし、backup後の分岐で同じ連番へ別内容が入っても、古い位置を別イベントとして読まない。

操作結果はWorkspace・認証済み主体・操作IDで保存する。要求digestは対象・操作・前提版・payloadからサーバーが作る。現在の認可を確認してから保存結果を照合し、未処理要求だけ前提版を比較する。

この初期schemaでは更新記録と操作結果を自動削除しない。cursorに時間の期限は置かず、Workspace・基準位置・続きの位置へ束縛する。位置が失われた、復元先に存在しない、連番に欠落がある場合はpendingのhistory_unavailableとして返し、snapshotの再取得が必要なことを呼出元へ伝える。snapshotとUIの切替は#8が実装する。有限の保持期間や自動削除はここでは追加しない。

## 検証と終了

rootの通常check/test/buildを維持し、実DB用の明示コマンドとLinux CIを追加する。標準Composeを元に、他の開発DBと分けた試験project・volume・ランダムなloopbackポートを作る。停止・復元・削除はその試験資源だけに限定し、既存の標準DBやOry内部テーブルを変更しない。

全ACの証跡を固定commitとともに別コンテキストへ渡して独立検品する。PRはRefs #4とし、全条件・検品・必須CI・マージ後照合を終えてからCloseする。新要件や未依頼の改善でこの範囲を増やさない。
