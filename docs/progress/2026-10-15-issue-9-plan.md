# Issue #9: Bleve検索・投影更新・再構築

- 対象: Issue #9、Scope revision 1、区分C。
- 基準: `a744639ee4aa7084e20a031fb114e4dd072c385b`。
- 現在の判定は[current-state.md](current-state.md)へ集約する。

## 目的と範囲

PostgreSQLのContext・版・直接所属からBleveの検索投影を構築し、認可済み候補と反映位置・完全性をGo業務APIへ返す。更新・削除・再送・順序逆転・停止・再構築中更新を照合し、必要な検索が不完全ならManifestを確定しない。

本文、固定参照、版、所属、権限の正本はPostgreSQLに残す。Documentの所属を子へ複製しない。検索順位で開始済みManifestを変更しない。検索GUIは#12、ArcadeDBは#10、実Run/CLIは後続Issueの範囲とする。

## 固定する条件

Issue #9のAC-1〜6、INVAR-1〜4を維持する。次の有限fixtureを末端の判定に使う。

| 条件 | 対象・期待結果 | 確認方法 |
| --- | --- | --- |
| AC-1 | 四粒度の日本語・英語・コード・IDを検索。Workspace、種別/ID/版、直接Scope所属、タグの絞り込みが正しい | 正解付き40検索と正負の絞り込みを固定。Document参照先と直接所属を区別し、ページ継続でも候補を重複・欠落させない |
| AC-2 | 索引に権限外のWorkspace/Contextがあっても、ID・本文・件数・継続から返却しない | 2 Workspaceと複数User、制限付きの参照先、途中の読取取消を含むAPI試験。SoTの現在認可と固定版を再照合 |
| AC-3 | 作成・新版・所属解除・削除、重複、古いイベント、反映途中の停止からSoTへ一致 | 実PGと永続Bleveで順序と停止を注入し、再起動後の候補ID/版/所属・checkpointを比較。既存の削除イベント契約も使い、削除UIは増やさない |
| AC-4 | 再構築前の索引を利用しながら、snapshot後の更新も新世代へ反映。検証前の切替なし | 再構築中に本文・所属を更新し、切替前の障害・再起動・再実行後に正本と候補・版・件数を照合。旧世代を不完全な新世代で上書きしない |
| AC-5 | Bleve停止・遅延・上限・要求版の未反映を区別。完全な0件へ補完せずManifestの確定を拒否 | 実検索とContext解決の統合fixtureで、利用不可/反映待ち/部分結果と、保存されたManifest件数を照合。既存Manifestは不変 |
| AC-6 | 合意した品質・負荷目標を満たす | 下記の固定データと測定で全項目を判定。未達なら同じ条件で原因と修正結果を記録し、目標を独断で緩和しない |

INVAR-1〜4は、Bleveを初期の必須検索とし、停止時のPostgreSQL検索への代替を禁止する。SoTの本文・固定版・認可、Scopeの直接所属、明示選択による入力確定を、上記の同じfixtureで照合する。

## 実装と調査の終了条件

1. 公式の採用版とAnalyzerを比較する。Bleve 2.6.1の取得と、日本語・英語・コードの小さなstandard/CJK比較は成功した。正解40検索で差を測り、API内の専用コンポーネントと独立配置に必要な責務を比較し、最小の構成をADRへ固定する。
2. 検索schema/Analyzerの版、索引の所有者と永続化、範囲・上限・cursor、現在認可とSoT版照合を実装する。Contextのタグを型付きメタデータとして扱い、本文入力へ自動注入しない。
3. 既存の更新記録と不変Contextを使って反映・checkpoint・再構築を実装する。新旧の業務更新経路は併存させず、SoT更新とBleveへ別々に直接書く方式は採らない。
4. 検索の範囲・反映位置・完全性を実際のContext解決へ渡し、AC-5の有限fixtureで確定の可否を判定できた時点で接続方法を確定する。検索結果の自動注入は行わない。
5. 実PG/Bleveの機能試験、合意負荷、必要な既存回帰、固定commitの独立検品、PR CI、マージ後照合を終える。

主要な変更先はGoの検索コンポーネント、Contextのメタデータと解決への接続、API起動、実試験とroot検証コマンド、ADR/手順/証跡。UI作業は含めない。調査は上記fixtureで採否を判定できた時点で終了し、未依頼の検索機能を追加しない。
