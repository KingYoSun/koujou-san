## 調査と実装の順序

最初に、公式配布済み版と専用実体のAPI契約を照合する。候補はGitea 28.2.0、Gitea Runner 5.2.0。最低対応版と、Issue / PR / commit / Actions / status / merge、認証、Webhookの対応表を固定した時点でこの調査を終える。Actions YAMLの類似性だけでAPI互換とは判断しない。

次に、既存の観測・起票・工程・Hopperの保存参照と認可資源を調べる。旧GitHubのwire・保存データの意味を保つ最小構成をADRへ固定してから実装する。候補は既存サービスへのGitea transportと明示的な外部識別の追加であり、別の起票Workerや実行エンジンは作らない。互換性を壊す必要が見つかった場合は、実装前に本人へ影響を示す。

対象pathは`apps/server/internal/githubobserve`、`publications`、`workflows`、`hopper`、`runs`、関連する共通UI、必要な最小の接続共用処理、検証コマンドと手順書。既存GitHubの認証方式や保存済みの権限IDは変更しない。

契約が未達のテストを先に再現し、観測・起票・既存利用側・画面へ接続する。専用環境でAC-7 / 8を確認し、局所検証後に固定commit・原AC / INVAR・必要仕様・観測結果を独立検品へ渡す。指摘は原条件の未達と今回の回帰だけを扱う。
