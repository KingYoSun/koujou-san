# Issue #8: 複数クライアントの同期・競合・切断復旧

- 対象: Issue #8、Scope revision 1、区分C。
- 基準: #7のマージcommit `70996e6669d8f85ef23b9e0f71337f6d74111e02`。
- 現在の判定はcurrent-state.mdへ集約する。

## 目的と範囲

権限内のContext・Scope・所属の確定版をsnapshotと差分で同期し、版競合・応答喪失・切断中の下書き・履歴不足を区別する。Web/Tauri共通画面で最終同期、古い可能性、未送信、要求の受付と観測済み結果を示す。実行報告の順序・欠落を扱う共通経路を用意する。

全文書の共同編集、切断中の自律実行、CLIの排他再開・割当・外部副作用、GitHub観測は対象外。Context編集全体は#12へ残し、本Issueは同期対象の閲覧・下書き・競合確認を実装する。実Run状態機械やCLIの成功判定を報告fixtureから作らない。

## 固定する条件と確認

Issue本文のAC-1〜6、INVAR-1〜4を維持する。

## 採用した判断

2026-10-15のユーザー判断により、サインアウト・Workspace権限失効を確認した場合は、そのWorkspaceの本文キャッシュと未送信下書きを削除する。再接続では下書きを自動送信せず、前提版が一致していても本人が内容を確認して明示送信する。

新規Run・割当変更・外部起票・pause回答は自動送信しない。操作ID・未確定要求と、通常の編集下書きは区別して保持し、結果不明の要求を別操作として繰り返さない。

## 実装と検証の順序

1. 同期通信・snapshot/差分の固定位置とcursor、取得時の現在認可、キャッシュ/下書きの保存と削除をADRへ記録する。通知は再取得のきっかけとし、欠落しても定期照合で確定状態へ戻す。
2. #4のstream/履歴と#7の不変記録を使う同期業務APIを実装する。snapshotはページ間で基準位置を保ち、差分不足では再snapshotを要求する。対象・依存する本文の現在認可を確認し、秘密値や端末パスを共有しない。
3. キャッシュはAPI接続先・User・Workspaceで分離し、未送信下書き・同じ内容で再送する未確定要求・確定状態を別に保存する。Web/Tauriの再起動で下書きを復元し、採用した失効時削除と手動送信を適用する。
4. 共通画面の同期状態、下書き、最新内容との競合確認・再適用へつなぐ。切断を実結果の成功へ置き換えず、開始操作をローカルだけで実行しない。
5. 報告の生成順序・欠落・重複・遅着を共通fixtureで照合する。実Run・Pause配送は後続担当へ同じ接続型を渡す。
6. 分離PG、Go/TS、2アカウントのWeb/Tauriの切断・応答喪失・競合・履歴不足、固定commitの区分C独立検品、CI、マージ後照合を終える。

## 調査の終了条件

保存場所と通信の具体形は、上記の有限fixtureと再起動・削除を実機で判定できた時点で確定する。通信できない間は最新権限を確認できず、最後に確認した時点のキャッシュであると表示する。再接続して失効を確認した後の再利用は拒否する。未実装のRunnerや外部起票を、同期基盤の成功だけで利用可能と表示しない。
