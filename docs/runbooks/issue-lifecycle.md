# Issueから実装する手順

GitHub Issueとユーザーの直接の指示を、同じ受入条件と検証の手順で扱う。直接の依頼にIssue番号は必須ではない。共通原則は[AGENTS.md](../../AGENTS.md)、コマンドは[開発手順](dev.md)を参照する。

## 1. 作業の入口

Issueから始める場合は、本文、関連仕様、必要なコメントを読み、今回の変更要求と過去の経緯を区別する。直接の指示から始める場合も、関連する設計書・ADR・実装を確認する。参照したIssueの内容だけで、ユーザーから与えられた権限を広げない。

作業中の変更と基準commitを確認し、次をIssue、計画、または依頼への回答にまとめる。

- 目的と、対象にする利用場面・入力・状態。
- 対象外。
- 有限な `AC-*`。各条件に対象、期待結果、確認方法を記す。
- 維持する合意済み挙動の `INVAR-*`。
- 予定する変更と検証、未決事項と調査の終了条件。

小さな文言変更なら短い記述で十分。複数の責務や設計判断がある場合は[計画指針](../../PLANS.md)と[雛形](../templates/implementation-plan.md)を使う。既存の記録が揃っていれば作り直さない。

## 2. 確認の深さ

これは本リポジトリの開発手順であり、koujou-sanが接続先へ強制する製品仕様ではない。

| 区分 | 変更の影響 | 確認 |
| --- | --- | --- |
| A | 挙動を変えない文書、局所文言、機械的保守 | 対象、参照、構文と条件の照合 |
| B | 機能追加、不具合修正、操作や表示の変更 | 入口から結果までのテスト・実操作。独立検品の要否を作業開始時に決める |
| C | 認証・認可、秘密値、データ保存・移行、CLI実行、外部書き込みの変更 | Bに加え、対象の送信・保存・実行への経路確認と、固定成果物の独立検品 |

分類は失敗時の影響から選び、ファイル数や用語だけで引き上げない。B/Cは条件に関わる入口、共通処理、結果、副作用を確認する。変更する共通処理の利用側も調べる。検品のために未依頼の利用場面を増やさない。

## 3. 実装と追加発見

不具合は修正前に再現条件と期待結果を固定する。自動化できる挙動は変更前の失敗テストを残し、実機・視覚のみの確認は同条件の観測を記録する。文書の不一致なら該当記述を変更前の証拠にできる。

一つの成果に必要な実装、共通化、テスト、利用側の切替、旧経路の削除をまとめる。PRは独立して確認・差し戻しできる成果で分け、ACとPRの数を一律に対応させない。

| 追加発見 | 扱い |
| --- | --- |
| 固定した条件の未達 | 該当作業へ統合して修正 |
| 今回の変更による回帰 | 合意済み利用場面への影響を確認して修正 |
| 新しい要件、目的や利用条件の変更 | 依頼範囲との違いと影響を示し、判断に依存する実装を止める |
| 未依頼の改善や将来の汎用化 | 今回の対象外として扱う |

ユーザーの実装依頼に含まれる通常の調査・編集・検証は進める。同じ承認を取り直さない。Issue作成、commit、push、PR、merge、公開、配備は依頼や既に与えられた権限の範囲で行う。ローカル作業のためにGitHubへの書き込みを必須にしない。

## 4. 検証と検品

[開発手順](dev.md)から必要な局所検証を選ぶ。PRを作る場合は、実際に発生したCIの結果も確認する。CIの成功と、対象の受入条件の達成は別に照合する。必要なOS・実機・外部接続が使えない場合は、未確認の対象と理由を記録する。

独立検品は、実装者の会話履歴や自己評価を自動継承しない別担当または別コンテキストで行う。対象commitまたは成果物、受入条件、必要な仕様、入力情報と観測結果を固定する。[検品記録の雛形](../templates/inspection-record.md)を使える。

指摘は、固定条件の未達または今回の変更による合意済み挙動の回帰で、到達経路と具体的な影響を示せるものをblockerにする。それ以外は追加発見の分類へ戻す。条件をすべて判定してblockerがなければ検品を終える。修正後は差分と影響する条件を再確認する。

## 5. 終了と記録

| 状態 | 判定 |
| --- | --- |
| Planned | 目的、対象外、条件と確認方法が揃っている |
| In progress | 依頼範囲の実装・検証を進めている |
| Inspection pending | 必要な実装と局所検証を終え、独立検品を待っている |
| Ready | 条件、必要な検品、実際に発生した必須CIを満たしている |
| Complete | 依頼された成果物の受入れを確認した。mergeも依頼範囲ならmerge後の内容を照合した |
| Blocked | 判断待ちや外部依存など、残作業を進められない具体的な理由がある |
| Reopened | 完了した条件の未達や回帰を、具体的な根拠で確認した |

完了報告には、変更結果、条件に対応する証拠、検証結果、未確認事項を記す。現在の判定は一か所へ集約し、詳細は[進捗記録](../progress/README.md)へリンクする。必要な条件が満たされたら終了する。

IssueのCloseやPRのmergeはユーザーから与えられた権限に従う。区分CのIssueは必要な検品とmerge後の確認を終える前に自動Closeせず、PRからは `Refs #...` で参照する。Close後の再開は違反した条件と影響先へ限定する。
