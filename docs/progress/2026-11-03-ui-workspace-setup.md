# UIだけでWorkspaceの作業を始める

## 目的と範囲

ユーザーは、開発フローとセットアップをkoujou-sanで完結させ、別途AIエージェントを前提にしないことを要求した。新しい作業原則5を適用する。基準は`9c87c24`、原則追加はPR #94。Giteaは既存アカウントのOAuthログインをkoujou-sanから開始し、Workspace管理者が接続を共有する方式を本人が選択した。専用Botは作らない。

今回の完了範囲は、初回の基盤と認証情報の準備後、通常のWorkspaceについてUIからLLM割当、Gitea認証、Project・repo・相談を準備し、相談を始められることである。既存の定義・Runの開始操作へも同じ設定から進める。サーバーLLMのOAuth本人認証、初回のGitea OAuthアプリ登録、端末固有のCLI認証・OS実行能力をWebへ暗黙に与えることは含めない。これらの準備後に設定ファイル編集や補助スクリプトを要求しない。

Workspace管理者は、中央の接続設定でアカウントと共有先を確認し、対象Project・repo・相談へ進む。サーバー管理者は、既存の認証済みLLM接続を対象Workspaceへ明示的に割り当てる。新規Workspaceへの一律許可や、Workspace管理者による他のサーバー資格情報の取得は行わない。

副ラベル・補足段落で導線を埋めず、必要な操作・入力・状態・エラーだけを表示する。既存PAT接続とファイル設定、固定版・現在権限を維持する。認証、接続保存、repo作成、Run開始を別操作とする。区分Cとして固定成果物の独立検品を行う。

## 実装と検証

`repositories`の既存暗号化・Gitea clientを拡張し、OAuthアプリ、期限付き認証状態、共有接続の確認・refreshを管理する。サーバーモデルのcredential登録は既存運用を維持し、Workspaceの割当はDBで保存して既存Gatewayの認可へ統合する。共有UIは既存のリポジトリ接続・サーバーLLM接続・Workspace画面を使う。

Go/TypeScriptの条件別試験、実フォームのDOM試験、専用DBと所有OAuth/HTTP、既存のforge/clientops/hopper/triage/usage等の影響する試験を実行する。認可・secret・保存・外部書込みは実装履歴を継承しない独立検品へ渡し、必須CI後にmergeする。

## 現在の判定

## 所有環境の証跡

`pnpm run test:forge`は試験専用PostgreSQLで既存観測・PAT接続を確認し、`TestWorkspaceSetupPostgres`で追加の認証・共有を検証する。UI試験はGo APIと所有OAuth HTTPを起動し、`workspace-setup.test.tsx`から通常のWorkspaceShellを操作する。認証入口だけを所有fixtureユーザーへ置き換え、Gitea app登録、LLM割当、Projectの編集・同期、repo作成、相談スレッドを実際のフォームとHTTPで保存する。外部の実アカウント、実LLM、実環境の既存ログイン状態は使わない。
