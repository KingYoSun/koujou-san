01 OPPORTUNITY

自律的に進む開発を、
共有できる工程にする。

kukuriでは、AIによる実装、独立した監査、CI、修正という工程が既に運用されている。次の課題は、その知識を特定のプロジェクトや担当者に閉じず、チームで変更・再利用できる形にすることだ。

論点現在の負担koujou-sanが目指す状態
工程の再利用手順や分岐が文書・Issue・セッションに分散し、変更に背景知識が要る。↗工程・道具・入力・戻り先を、独立した定義として編集できる。
品質の判断CIの成功、監査の合格、実機での未確認が、一つの「完了」に混ざる。↗基準と証拠を対応させ、合否と判断不能を分けて扱う。
チームの参加状態確認や次の指示を人が仲介し、背景を知らない人が参加しにくい。↗目的・成果・判断点をGUIで共有し、担当する確認や回答に参加できる。
対象は、多数の工程と大量のContextを横断して扱うチーム。最初はkukuriの一つのIssueで一巡させる。既存のCLI・GitHub・CIを維持しながら、観測から工程の制御へ導入を進める。
02 FOUNDATION

小さなRunを、自由に組み立てる。

個別の作業は共通の最小単位に揃える。その上で、使う道具、渡す情報、検品の方法を工程ごとに選べるようにする。

01 / TOOLS

道具を選べる

任意のCLIを実行する。実装と検品で別のハーネスを使い、既存のリポジトリとCIへ接続する。

02 / QUALITY

検品を設計できる

テスト、監査、UI・UX、実機、人の判断を組み合わせ、製品に合う完了条件を定める。

03 / CONTROL

実行せず調整できる

GUIで工程や入力を確認・編集する。定義の変更と実行の開始を、別の操作として扱う。

Runすべての作業に共通する実行単位

  • context任意
  • prompt任意
  • command必須
02pause

途中の質問や外部の結果を待つ。回答を受けて、同じRunを再開する。

03output

複数のRunをつないでWorkflowを構成する。順次・並列・合流・分岐・差し戻しを表現し、終了した作業のやり直しは、新しいRunとして記録する。

03 CONTEXT

再利用する文脈。
検品には、選び直した文脈。

製品哲学を共有しながら、検品の独立性も守る。情報を小さな単位で組み合わせ、Runごとに注入する内容・順序・版を明示する。Scopeに属するだけで、すべての情報が渡ることはない。

文書を組み立てる軸 COMPOSITION
Sentence→Paragraph→Section→Document

一文から文書全体まで、どの粒度でも参照・再利用する。

所属を整理する軸 SCOPE
Product→Project→Milestone→Issue

各文書単位をScopeにGroupingする。文書構造とは独立して管理する。

判断を再現できる記録。

分離の実効性も確認する。
ハーネスの履歴・共有メモリ・実行環境まで含めて、必要な独立性を検証する。

04 EXPERIENCE

人は意図を伝え、判断に参加する。

大量のContextの選択や、結果を知識へ戻す作業をLLMが支える。非エンジニアや新しい参加者も、今回の目的と自分に求められる判断をGUIから理解できるようにする。

  1. 必要なContextを選ぶ

    許された範囲を検索・探索し、選択理由と実際に渡す情報を確認できる。

  2. 自由入力からRunを定義する

    「このIssueを修正したい」という依頼から、利用できる道具と入力を組み立てる。

  3. outputを次の知識にする

    作業結果から再利用できるContextを生成し、由来付きで登録・更新する。

三つの機能は、Runの上位にあるクライアントの操作レイヤーに置く。MCP経由でサーバーの情報と操作に接続する。

想定画面 / 操作イメージ
kukuri / Issue / 成果の確認

入力中の文章を失わずに、
画面を切り替えたい。

あなたの確認を待っています
今回の判断点
プレビューで文章を入力し、画面を切り替えて戻ってください。入力内容は保持されていますか？
自動テスト確認済み
対象の操作体験人による確認待ち
結果と証拠を返す問題を伝える
受入条件・対象ビルド・元の証拠へ辿れる
自動処理と手動編集は、同じデータを使う。
提案として受け取るか、設定した範囲で自動反映するかを選べる。人は生成結果を修正し、判断や項目を固定できる。履歴と版を分断しない。
05 CONTINUOUS LOOP

結果から仕事を生み、
次に取り組む順序を整える。

Hopperが発見を次のIssue・Runへつなぎ、TriageがIssueの優先度を判断する。サーバーで処理を継続し、作業の取りこぼしと、人による整理の負担を減らす。

  1. Issueを受け取る人の起票・外部取り込み・Hopperからの発行
  2. Triageで優先度を付ける製品方針と根拠に沿って判断
  3. 実装Run → 検品Run割当条件を満たして着手し、基準と証拠で確認
  4. Hopperが各Runの結果を評価する条件に応じて、新しいIssueまたはRunを発行
Issueは再びTriageへ。Runは実行条件が揃うまで待機する。検品の不合格は修正へ、判断不能は追加確認へ戻す。

Triage・Hopperは、工程を制御するサーバー機能。Runの派生形にはしない。

Hopper / Create next work

発見を、仕事に変える。

結果に基づく決定論的な条件と、LLMによる意味判断を組み合わせ、IssueまたはRunを発行する。

決定論的：nightly CIの失敗 → 調査用Run
意味判断：実装中に見つけた未対応バグ → Issue

発行の根拠と由来を保存し、重複・連鎖の上限・予算を管理する。提案と自動発行を選べる。

Triage / Set priorities

優先度に、理由を持たせる。

製品哲学、影響、緊急性、期限、依存関係を、選択したContextと評価方針に沿って判断する。

Hopper・人・外部サービスのIssueを共通に評価。
方針や状況が変われば、対象を絞って再評価する。

AIの推奨と採用中の値を分け、人は手動で固定できる。優先度を変えるだけでは、Runを起動しない。

判断の根拠と版を記録重複発行を抑止連鎖と費用の上限手動固定を保護不明を低優先度と扱わない

クライアントがオフでも、次の仕事を準備する。
サーバーが取得できたCI等の結果から評価・発行を進める。実行可能なRunnerがいないRunは待機し、未同期のローカル結果は推測しない。

06 COST & QUALITY

品質と費用を、同じ工程で見る。

各Runで実際に使ったモデルとトークン消費量を記録し、費用を可視化する。初期のコスト最適化は、計測・比較・人による設定改善を中心に据える。

受入れに至るまでの
総コストで比較する。

実装の一回分に加え、失敗・修正・再検品も含めて評価する。検品結果、手戻り、時間と並べ、Contextやモデルの選択を見直す。

Run実行クライアントのLLM操作Hopper評価Triage評価

費用の帰属を分け、全体集計では一度ずつ数える。

見えるようにするもの判断に必要な区別
モデルと利用量実際のモデル、入力・出力トークン、取得できた内訳、再試行・失敗。
金額の根拠報告された金額、単価からの推定額、定額契約等のAPI料金換算額を区別する。
計測できない部分一部取得・未取得・未算定を明示する。不明な消費を0として表示しない。
比較の条件工程・Context・料金の版と計測範囲を残し、品質や作業難度も合わせて読む。
TOOL FREEDOM

CLIとゲートウェイから取得可能な利用量を集める。計測に未対応のCLIも利用できる構成とし、すべての実行を特定のゲートウェイへ集約することは求めない。

07 ARCHITECTURE

状態はチームで共有し、
実行は選んだ環境で行う。

共有状態を持つAPIサーバーと、ハーネスCLIを動かせるネイティブクライアントを基本構成にする。依頼する人と、作業を実行する端末を分けて扱う。

CLIENTS / TEAM

確認・編集・実行

ネイティブアプリ

共通GUI ＋ ローカルRunner。登録された端末で、任意のハーネスCLIを実行する。

Tauri
Webフロントエンド

進捗確認、定義の編集、起票、質問への回答。ローカルCLIの実行機構は持たない。

APIで状態を同期 / 操作レイヤーのLLMはMCPで接続

SERVER / SHARED CONTROL

Go API ＋ Worker

共有状態・権限工程・実行割当MCPHopperTriage外部CIの観測
PostgreSQL正本 / SoT
Bleve全文検索
ArcadeDB関係探索

本文・関係・版・状態の正本はPostgreSQL。検索・グラフは更新を反映し、再構築可能にする。専用の検索・グラフエンジンは初期から必須。

領域構成と位置付け担うこと
共通フロントエンド構成方針TypeScript / React / shadcn / Zustand / TanStack QueryWebとTauriでGUI・状態表示を共通化。
認証標準同梱Ory Kratos ＋ HydraログインとOIDC。Workspace・端末の権限はkoujou-sanで管理。
クライアントの推論接続第一候補Manifest LLM GatewayContext選択、Run定義生成、outputからのContext生成。
サーバーの推論接続第一候補Bifrost OSSHopperの意味判断とTriage。業務処理はGo側で制御。

二つのゲートウェイは交換可能な接続として検証する。採用版・配置・同梱は未確定。CLI自身のLLM接続とは分け、GitHub上のリポジトリとGitHub Actionsの配置を維持する。

08 DELIVERY PLAN

初期から、一巡できる製品にする。

チームで依頼し、実装し、検品し、次の仕事へつなぐ体験を初期リリースに含める。GUI、Context、LLM操作、コスト計測、Hopper、Triageを同じ工程に接続する。

01 / Team

共有と認証

Go API、Ory、Web・Tauri、参加者と端末の権限、状態同期。

02 / Workflow

実行と検品

任意CLI、pause、工程編集、分岐・差し戻し、成果と証拠。

03 / Context

構造化と選択

四段階の文書単位、Scope、版、無注入・選択注入、検索・グラフ。

04 / Assistance

LLMによる操作支援

Context選択、Run定義生成、結果の知識化。自動反映と手動編集。

05 / Loop

HopperとTriage

Issue・Run発行、自動優先度付け、理由・履歴・手動固定。

06 / Improvement

費用と品質の比較

モデル・トークン・費用、計測範囲、工程やScope別の集計。

kukuriで使いながら、順に成立させる。

開発順序の案 / 期間・工数は未見積もり
A

共有・検索・観測

複数クライアントで同じ状態を見て、Contextの検索と関係探索を行う。

B

一巡の制御

実装・質問・独立検品・差し戻しをつなぐ。決定論的Hopperを接続する。

C

編集と交換

道具とContextを交換する。LLM操作、意味判断のHopper、Triage、比較画面を揃える。

他のプロジェクト

性格の異なるリポジトリに適用し、固有の規則を設定へ分離できたか確かめる。

後続で扱う範囲複雑なWorkflowの動的生成、プラグイン市場、全CIサービスへの対応など。費用だけを目的にした自動モデル選択は、初期の必須機能にしない。
09 VALIDATION

使った結果で、価値を確かめる。

kukuriの現行運用を比較起点にする。近い性質の作業で、人の負担、検品の有効性、費用、工程の変更しやすさを観測する。目標値は比較起点を測ってから決める。

First proving ground

kukuri

日常の一つのIssueを、依頼から成果の受入れまで追う。そこで生じる待ち・修正・判断を、製品を改善する材料にする。

道具を交換しても、
検品とチームの判断が
つながり続けるか。

  • 参加と運用初見の人が判断点を理解できるか。指示・状態確認・再開に使う時間はどう変わるか。
  • 検品の有効性既知の欠陥の検出、誤指摘、合格後の不具合を確認する。指摘数だけで品質を測らない。
  • Contextの選択必須情報の見落とし、不要な情報の混入、選択・生成後の手動修正量を観測する。
  • 費用と時間手戻りを含む費用、待ち時間、計測範囲を比較する。推定額と実支払額を区別する。
  • 循環の質Hopperの誤起票・重複・回収漏れ、Triageの根拠・手動修正・緊急Issueの見落としを確認する。
  • 拡張と共有別CLI・別リポジトリの導入に要る変更量と、同期・切断復帰・競合時の挙動を確かめる。

実装に向けて、次に具体化すること

接続と実行の契約Run・pause・Contextの具体的な形式、初期OS、CLIの対話・計測範囲、独立検品の分離方法。
規模と運用Context件数と探索負荷、性能目標、各エンジンの配置・復旧、ゲートウェイの採否と配布構成。
OSSとしての公開koujou-san自体のライセンス、貢献方針、初期化・更新手順。選定した構成を実運用で検証する。

道具を選ぶ。文脈を選ぶ。
チームで、品質を確かめる。

koujou-sanは、その判断と作業をつなぐ工程をOSSとして共有する。kukuriで使い、変え、別のチームでも使える形へ育てていく。
