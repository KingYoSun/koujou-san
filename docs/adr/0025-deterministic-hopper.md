## 判断

初期テンプレートは自動発行とし、Runは通常の割当・開始へ渡す。定義の保存、有効化、過去結果への適用を別操作にする。有効化だけで過去の結果を再発行しない。管理者が処理主体・枠・有効状態を管理し、実行依頼の許可は別に確認する。

起点の初期上限は深度3、累積発行10件、評価100回、24時間、評価ごとの発行1件とする。管理者は変更できる。起点で確定した上限と累積値をIssue・工程・複数Hopperへ引き継ぎ、新しい定義や工程へ移るだけではリセットしない。既存の起点の上限変更と再開は、対象を指定した明示操作にする。Hopper由来の結果を監視するかは定義の`include_derived`で指定する。

別Runの同じ問題は、リポジトリ・対象・規則・結果内の識別値で照合する。初期方針は未完了Issueへの関連付け、完了済みだけの場合は再発提案とする。照合期間、重複候補の保留、再発としての発行は定義で変更できる。文章の類似では統合しない。

条件は型付きフィールドの`eq / in`、順序を持つ`all / any / not`とする。ANDは偽、ORは真で短絡し、それ以外では判断不能を伝播させる。CI結論、プロセス終了コード、検品判定を混同しない。必要な未同期ログは入力待ちにする。任意shellやLLMを条件の評価に使わない。

## 確定と再送

受理したRun結果は所有Domainの共有transactionから、GitHubの観測は変更版の確定transactionから要求へ接続する。元イベント・結果版・定義版で一意な既存Worker jobを作る。対象・契機の索引と過去結果のキー索引を使い、Context全件や全Run履歴の走査を通常操作へ置かない。

既存StoreのCAS・receiptを、呼出元が所有するtransactionからも使えるようにした。Run・Context・起票のサービスは、そのtransactionだけに束縛したコピーから共通の検証と保存を呼ぶ。評価、行動の識別、同一問題の予約、起点の枠、内部の作成を同じtransactionで確定する。内部の発行に失敗した場合はsavepointから戻し、部分的なRun・Scope・起票要求を残さず、評価の保留理由を保存する。

外部Issueは#22の共有要求・送信意図・HTML識別子・作成後の確認・結果不明の照合を使う。外部作成を独自に実装しない。Workerが発行後・完了記録前に消失しても、次のleaseは同じ評価と作成済み要求を使う。

自動開始を選んだRunは、同じRunの割当待ちを永続化する。現在の管理設定、実行依頼者、入力の受取権限、接続・能力を確認し、既存の`Run.Assign`へ渡す。Runner不在なら待機し、復帰しても別Runを作らない。GitのRepositoryと固定commitを宣言した場合は、通常の割当が作る専用worktree・branch情報を使う。APIサーバーはCLIを起動しない。

## 由来と権限

通常の入力・工程への継承では起点と深度を維持し、Hopperによる新しい発行だけ深度を1進める。IssueのScopeから工程へ渡す由来は`Start.sources`の固定参照で指定する。既存Workflowが、同じ結果・再試行先のRunDefinitionを担当している場合は、Hopperが修正Runを重複発行しない。

由来の正本はPostgreSQLに置く。ArcadeDBは固定したDomain参照と由来から関係を投影し、再構築する。発行枠や権限をグラフの反映状態で決めない。参照・検索は現在のWorkspace、資源、固定版、操作範囲と分類を検証する。工程や入力の参照から権限を付与しない。発行先の入力へ実装履歴を暗黙に注入しない。

MCPの編集と管理は`hopper-edit / hopper-manage`の目的を分け、readやContext編集へ追加しない。管理目的でも現在の管理者権限と個別の実行許可は必要である。参照だけの操作は評価・発行・開始を増やさず、leaseや資格情報を返さない。

## 費用と定期観測

起点に任意の費用上限を指定できる。発行したRunの記録済み費用は、既存Workflowと同じ共通処理で、一つの評価種別・通貨ごとに見る。未取得、未算定、遅着、参照不能を0にせず保留する。上限で止めるのは追加の発行・開始であり、開始済みCLIの実請求額上限を保証しない。

GitHub Actionsは固定Runの観測に加え、workflow IDとイベント種別を指定した最新周期の観測へ対応する。公式の[workflow実行一覧](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-workflow)を読取り専用で取得し、選んだRunと実行回の取得・照合は既存経路を使う。新しい周期は別の起点になり、前周期の連鎖停止を永久停止にしない。定期照合で観測していない全過去周期を、取得済みとは扱わない。

## 検証

専用PG・ArcadeDBと所有するHTTP fixtureで、条件、同時取得、応答喪失、発行後のWorker消失、同一問題、再発、連鎖、工程の再試行、現在権限、費用欠測、Runner復帰、定期CIからの一巡を確認する。共通UI・HTTP・MCPの対応と独立検品、最終CI、merge後照合は[証跡](../progress/2026-10-17-issue-25-evidence.md)へ記録する。
