# ADR 0027: サーバーLLMによるHopperの意味判断

- 状態: Accepted。2026-10-18の本人回答を反映。
- 対象: Issue #27。[受入条件と対象外](../progress/2026-10-18-issue-27-plan.md)。

## 判断

Bifrost OSS HTTP 2.3.0を、標準Composeの任意サービスとして同梱する。imageはdigestで固定し、専用SQLite volume、管理認証、Worker用virtual keyを分ける。クライアントのRig、RunのCLI認証とは共有しない。BifrostはモデルHTTPの中継を担当し、共有状態の確定・認可・Hopper発行はGoとPostgreSQLが担当する。

初期値は入力1 MiB、出力4096 token、要求120秒、Worker最大2試行、Workspace同時2評価とする。定義と自動化設定で変更できる。入力上限は最終要求のUTF-8サイズへ適用し、超過時は省略せず入力待ちにする。Gatewayのretryは0、cacheと本文ログは無効とし、fallbackは定義に明示した許可モデルだけを要求する。

必要な証拠の遅着・変更と元結果の訂正では、関係する評価だけを別履歴で再評価する。定義や評価Contextの編集で全履歴を再評価しない。過去結果への適用は、対象とページ範囲を指定する別操作にする。膨大なContextを通常操作で列挙せず、固定参照と選択条件、証拠IDの索引を使う。

## 入力・外部作用・採用

意味条件を含んでいても、通常条件だけで結果が確定した場合は推論しない。現在の自動化主体・起点の停止と上限を確認し、固定結果・必要な証拠・評価Contextを取得する。操作の送信禁止分類と現在の権限を、取得前、要求予約前、採用前に検証する。

要求の固定入力、送信前予約と利用量の仮記録、原応答、採用評価を別に保存する。HTTP中にDB transactionを保持しない。同じ予約を再送せず、保存済み応答は再利用する。応答保存前に失われた要求は欠測として残し、別試行の消費と区別する。要求後の権限失効でも、予約済みの原応答と利用量は保存するが、発行は許可しない。

モデルは成立・不成立・判断不能と候補・引用を返す。引用は送った固定参照と原文へ照合し、候補の状態は「疑い」か「要再現」に限る。形式不正・時間切れ・接続障害を不成立に変換しない。モデルの文章でテンプレート・権限・コマンドを変更しない。評価用のContext・ログと、発行先や独立検品へ注入する入力は分離する。

不成立・判断不能・失敗・再試行の消費は、そのHopper評価へ帰属させる。全試行の料金版をWorker結果へ保持し、連鎖ではcoverage groupごとに一度だけ集計する。Gatewayのfallback応答が最終providerのusageしか報告しない場合、合計は欠測とする。費用欠測を0へ変換しない。

## 保存と運用

Gatewayの本文ログは初期無効。Go側では追跡に必要な固定入力・原応答・採用履歴を保持し、現在の依存権限を読取りにも適用する。管理APIと推論APIには別の認証を使う。設定JSONをGateway設定の正本とし、管理画面だけで変更した設定は再起動で置き換わる。設定・SQLite・暗号鍵・provider認証を一組として保全する。

Gatewayが停止しても、決定論Hopper、閲覧・編集、手動操作は使える。意味判断だけを上限内の失敗・保留にする。運用手順・版・外部通信・復旧・ライセンスは[サーバーモデル接続](../runbooks/server-models.md)、検証済みの事実は[証跡](../progress/2026-10-18-issue-27-evidence.md)を参照する。
