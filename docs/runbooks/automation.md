# Triage方針・優先度・処理状態

Workspaceの「Triage方針・優先度・処理状態」で、方針の版、優先度、評価入力・原応答、利用量・費用、外部同期を確認する。ページは50件ずつ取得する。Hopperの定義・発行は[Hopperの手順](hopper.md)、モデル接続と任意Bifrostは[サーバーモデル接続](server-models.md)を参照する。

## 方針と優先度

編集者・管理者は「初期テンプレートで新しい方針を作る」からP0〜P3を読み込める。名称・段階数・順序・基準は変更可能。対象Scopeと方針の優先順を設定する。一つのIssueへ適用する方針は独立して選び、同順位で競合する場合と未設定の場合は評価待ちにする。Scopeへの所属で閲覧権限を付与したり、複数方針を暗黙に合成したりしない。

「モデル接続を取得」からWorkspaceに許可された接続を選び、要求モデル・指示・上限を設定する。Contextの選択、必要な参照、fallback、固定料金版は詳細JSONに指定する。Contextの`head`は要求時に固定し、`none`ではContextを送らない。除外や送信禁止分類を守り、容量超過では省略せず保留する。クライアントやCLIの認証は使わない。

方針の保存は版を追加する。管理者は保存した固定版を有効化でき、自動反映の有無を指定する。新しい版を保存しても有効版は自動で切り替わらない。有効化だけで過去の全Issueへ要求を追加しない。対象の変更・参照の変更・期限は、関係するIssueへの要求へまとめる。

Issueの優先度を取得し、理由と優先度を指定すると手動固定になる。固定中も新しい推奨は記録されるが、採用値は維持する。固定解除は現在の対象版・有効な方針に対応する推奨だけを反映する。未評価・失敗・情報不足・再評価待ちは優先度の値とは別の状態であり、既存の値を最低優先度へ変更しない。

「Issue情報を取得・編集」では、既存Scopeと分けて本文・状態・期限・固定参照の依存を保存する。期限は7日前・24時間前・到来時に評価する。依存先の状態と、選択Contextを入力へ固定する。未計測の工数・費用・影響人数は不明のまま残す。

一覧は採用尺度の固定版ごとに並び、異なる尺度を無条件に比較しない。関連付けたRunは採用値と依存先の完了を待って通常の割当へ進む。Runの入力に`issue: {id: "scope:ISSUE_ID", version: "FIXED_VERSION"}`を明示して関連付ける。割当の実行許可・能力・検品・処理枠は別に検証し、優先度変更でRunを作成・中断しない。

「根拠・不明点・消費」から試行を開き、引用と固定参照、未確認情報、利用量と固定料金版へ進む。一覧は新しい入力・原応答の本文を含まないメタデータを取得し、本文は固定版を明示して開く。

## 一括評価

保存した方針から、受付期間・Scope・総件数・1ページの件数・費用上限を指定する。基準時刻・共有位置・継続カーソルを保存し、「保存した条件で次のページを要求」で続ける。基準より後の新規Issueは含めず、保存した共有位置のScope階層で対象を判定する。各要求の本文は受付時の現在版から固定する。

要求の受付完了とモデル評価の完了は別である。先行要求の消費・料金が未確定なら待機し、モデルの試行回数を消費しない。上限や欠測を0として通過せず、停止した一括評価は新たに送信しない。全件の定期評価は初期無効。

## GitHub優先度の同期

管理者が方針にGitHub接続IDと、各段階に対応する既存ラベルを設定する。Issue情報へ接続IDとIssue番号を関連付ける。Hopperの起票から作ったIssueでは、外部の作成確認後に、方針の接続に一致するものを関連付ける。

外部反映には管理者の現在の対象更新・実行許可も必要であり、Hopperの権限を引き継がない。送るのは優先度ラベルだけで、本文・状態・非公開の理由・証拠は書き換えない。GitHubの本文・状態の観測は、ローカル本文と別に保持する。

保存した採用値と書込意図を使って照合する。失敗や応答喪失では先に観測し、LLMを呼び直さず再送する。外部の人の変更は固定として取り込み、最後に確認した手動判断から内外が変わった場合は競合を維持する。解消時は理由を付けて採用値を選ぶ。変化のない定期照合では新しい共有履歴を作らない。

初期の照合間隔は60秒。起票App設定の`priority_interval_seconds`で変更できる。APIのRetry-After・残量に従い、取得できない間は保存した値と最終取得時刻を表示する。

## 管理者の設定

Hopper/Triageごとに設定を読み込み、有効状態、対象取得、結果確定、同時処理枠、試行上限、担当・処理期限、再試行間隔、期間内の試行上限を保存する。保存した管理者の現在のWorkspace権限を確認する。ログアウトだけでは無効にならず、管理者の離脱・役割変更・対象権限の失効・管理設定の停止では取得や確定を保留する。クライアントのCLI認証や個人キーをコピーしない。

新規Triage設定の初期値は、モデル入力1 MiB・出力4096 token・120秒・最大2試行・Workspace同時2評価。保存済みの値は読み込んで使い、新しい初期値で上書きしない。

費用上限を使う場合は、上限・通貨・評価種別を指定する。#14の固定費用評価を使い、異なる種別や通貨を合算しない。利用量が欠測・参照不能なら保留し、0として続行しない。実際の利用量の遅延がある場合、件数上限を併用する。

停止は未確定の処理に適用し、確定済み副作用を取り消さない。設定・権限を復旧した後は、履歴を確認して明示的に再開する。再開時も現在の対象版・方針・権限を確認する。根拠が変わった古い要求は再利用せず、現在の対象へ明示適用する。

## APIとMCP

- `GET /automation/workspaces/{workspace}/template`: 初期の編集可能な優先度尺度。
- `GET /automation/workspaces/{workspace}/model-template`、`model-connections`: モデル設定の編集初期値と、許可された接続。秘密値は返さない。
- `GET/POST /automation/workspaces/{workspace}/records/{id}`: 固定版の取得、期待版と操作IDを持つ保存。保存可能な種類は`policy / activation / control / priority / issue / batch`。モデル入力・原応答・同期は所有処理が保存し、固定版で参照できる。
- `POST /automation/workspaces/{workspace}/query`: 従来の`heads / records / jobs / history / priority / selection`に加え、`priorities / evaluations / attempts`で優先度順・有界な評価メタデータを取得する。個別・一覧とも現在の権限を確認し、根拠が非公開なら結果へ含めない。
- `POST /automation/workspaces/{workspace}/apply-past`: 固定方針、継続位置、最大100件の明示適用。結果に要求数と次の位置を返す。
- `POST /automation/workspaces/{workspace}/jobs/{id}`: 管理者による停止・明示再開。共通CASとreceiptを使う。

MCPは`triage_get / triage_query / triage_set / triage_apply_past / triage_job_control`を提供する。通常のクライアントから編集目的または管理目的を先に作り、現在の役割と資源別権限の範囲で操作する。read/Context editだけでは編集できない。Workerのlease値・checkpoint本文は公開しない。

## 開発・検証

`pnpm run test:automation`は専用PG・所有モデルHTTPで受理、再送、並行取得、手動固定、期限、Context、消費、割当、一括評価とラベル同期を確認する。`pnpm run test:mcp`は実Oryと公式SDKでHTTP/MCPの共通経路を確認する。`pnpm run test:triage:ui`はTriage用の所有モデルと共通画面を起動する。

実モデルの試験入口は`pnpm run test:triage:live 接続設定JSON 許可台帳JSON`。一接続・一モデル・試験Workspace `one`、合成の二入力、各4 KiB・2048 token・30秒・fallback/自動retryなしに限定する。`--owned`なら外部通信なしで同じ入口を確認できる。台帳の要求枠は再実行でも戻さず、失敗しても超過要求を送らない。

GitHubの実接続は`pnpm run test:triage:github-live 起票App設定JSON 許可台帳JSON`。準備した内容へ本人の許可を得た後だけ実行する。対象は`KingYoSun/koujou-san`の合成Issue一件と一時ラベル二件、Appのラベル反映と既存ghログインによる外部変更一回。終了時にそのIssueをCloseし、その二ラベルだけを削除する。本文・状態を変更しないという判定は、作成と終了時の片付けを除く同期区間で行う。

結果を所有するDomainは、実際に共有受理するtransactionから`AcceptResultTx`を呼ぶ。端末の完了観測や未取得ログを受理の代わりにしない。後続Domainの実行器は`RunOne`へ接続し、外部I/Oはtransactionを保持せず行う。結果と再開位置はDBへ保存し、再取得後に外部呼出しを無条件に繰り返さない。
