# 0015: 共有受理と永続要求、Triageの方針と手動判断

- 状態: Accepted
- 日付: 2026-10-16
- 根拠: Issue #15、設計書§6.12・6.13・7.14〜7.16・12.6・12.7、初期動作三点へのユーザー回答

## 判断

優先度の初期テンプレートはP0（緊急）・P1（高）・P2（通常）・P3（低）とする。方針ごとに識別子・名称・意味・段階数・順序を変更でき、製品の固定尺度にはしない。通常の手動変更は固定し、固定中の新しい評価は最新推奨だけを更新する。固定解除時は現在の入力と有効な方針に対応する推奨だけを採用する。採用理由と最新推奨の理由を分け、処理失敗や未評価を最低優先度へ置き換えない。

方針の内容と優先度は既存の編集権限に従う。有効化・自動化主体・処理枠・予算はWorkspace管理者が管理する。方針の保存と有効化は別の記録とし、有効化は固定した方針版を参照する。保存・有効化だけでは過去対象の要求を作らない。過去への適用は対象と継続位置を確認したページ単位の明示操作にする。

既存Storeへ、受理した変更と同じtransactionで要求を保存する呼出しを一つ接続する。現在のIssue Scope更新はここからTriage要求へつなぐ。端末の完了観測は結果受理とは異なるため、`sync-report`の完了フラグやログからHopper要求を推測しない。結果を所有するDomainには`AcceptResultTx`を提供し、そのDomainが結果を確定するtransactionから呼ぶ。#16以降のRun受理はこの契約へ接続する。

要求は元イベント・対象版・方針/定義版で一意にする。PostgreSQLで担当・lease・期限・試行・再開位置・結果を保存する。Hopper/Triageごとに処理枠を予約するため、一方の大量要求で他方を無期限待機させない。外部処理はtransactionを閉じてから呼び、保存した結果は再取得後に外部呼出しを繰り返さず確定できる。

APIと同じGoプロセスで使えるWorker関数を採用する。複数プロセスからも同じPGの予約・leaseで排他する。別のqueue製品や汎用Workflowエンジンは導入しない。実際の実行器は後続のHopper/Triage Domainが接続し、基盤のために仮のLLM評価や発行処理を製品へ追加しない。

自動化主体はWorkspaceと処理の種類に属する管理設定として保存し、設定した管理者の現在のWorkspace権限を使う。ログインセッションや個人の端末資格情報には依存しない。取得・確定では有効状態、取得/確定の許可、管理者の現在の役割、対象と根拠の閲覧権限、対象版・有効な方針版を再確認する。失効や根拠変更は保留し、過去の結果と優先度を保持する。

期間内の試行上限と、必要なら記録済み費用の上限を使う。費用は#14の固定評価参照を、一つの評価種別・通貨で重複を除いて集計する。欠測・参照不能な費用は0へ補完しない。利用量の遅延がある経路で、厳密な実請求額上限を保証しない。

方針・優先度・要求・履歴は共通のHTTP/GUI/MCPサービスで取得する。MCPの編集には通常認証から明示した`triage-edit`、管理操作には管理者による`triage-manage`の目的を使う。既存のContext編集やreadへ権限を追加しない。MCP toolは自分の目的や権限を作成できない。処理のlease値と再開用checkpointの本文は公開応答へ返さない。

## 選定と検証

共有受理と要求を別transactionで書く方式は、途中停止で一方だけ残るため採用しない。揮発キューとプロセス内だけの排他は再起動・複数Workerで所有を維持できないため採用しない。別queue製品は本条件を満たすために不要であり、PGへ保存・予約・回収を集約した。

元データの保存前・保存後・要求保存後の停止、二Workerの同時取得、lease失効と別所有者による回収、外部処理待機中の単一接続poolからの別query、Triage100要求とHopper1要求、役割・主体の失効、手動固定と解除を専用PGで検証する。方針選択は四段階のScopeと索引を使い、Context全件や全バックログの本文を取得しない。

初期段階で実装するのは永続要求と処理契約・共有状態である。決定論Hopperの発行は#25、サーバーLLMによるHopperは#27、TriageのLLM評価・外部同期は#28で接続する。
