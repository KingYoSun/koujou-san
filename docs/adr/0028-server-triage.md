# ADR 0028: サーバーTriageの評価・採用・外部同期

- 状態: 採用。#28の実装・受入検証は進行中。
- 前提: [ADR 0015](0015-automation-foundation.md)、[ADR 0027](0027-server-hopper-semantics.md)。
- 本人の判断: GitHubラベルの双方向同期、優先度採用待ちと同順位の受付順、期限の3境界、Hopperと別のモデル上限。

## 入力と採用

既存のIssue ScopeはGroupingの契約を維持する。本文・状態・期限・依存・由来を、Scopeに関連付けた版付きの`issue:`記録へ保存する。人・Hopper・外部取り込みを同じ受理経路へ接続し、外部の本文・状態の観測はローカル本文と分ける。

有効な方針の固定版、尺度、基準時刻、Issue情報、依存先の状態、選択Contextを入力として固定する。Contextの`head`は要求時に解決し、選択結果のManifestと参照版を保存する。`none`はContextを送らず、除外した内容は入力へ含めない。工数・費用・影響人数の欠測を実測値として補わない。

モデルが返せるのは、方針に含まれる優先度または判断不能、理由、固定参照と引用、不明点だけである。Issueの本文を方針や命令として扱わず、Run・command・pauseやIssue本文の変更をモデルの作用にしない。

要求を送る前に、現在の主体・権限・送信禁止分類・モデル接続・上限を確認する。反映前にも入力版・有効方針・権限を確認する。新しい入力の要求ができたら古い要求を置き換え、返ってきた原応答と消費は履歴へ残す。手動固定中は推奨だけを更新し、解除時は現在の入力と方針に有効な推奨だけを採用する。採用値の尺度の版を保持し、異なる尺度を無条件に比較しない。

HopperとTriageは同じGateway、応答解析、要求の送信・完了保存、利用量・費用の保存処理を使う。主体・入力・モデル・上限・処理枠は分ける。送信前に利用量の予約を保存し、送信後は取消や権限失効があっても、その予約に対応する原応答と消費を保存する。保存済み応答を再利用するときに同じモデル要求を送らない。欠測や単価未登録を0円にしない。

## 再評価と件数

本文・依存・有効方針・選択参照の変更は、利用関係の索引から対象を絞る。変更の処理は100件ずつカーソルを進め、Workspace全体のContextを列挙しない。優先度・理由・処理状態や自分のラベル同期の再通知から、評価を再発火させない。

期限の7日前・24時間前・到来時に評価する。次の期限時刻の索引を使い、停止中に複数の境界を過ぎた場合は現在の要求へまとめる。全バックログの定期評価は初期無効とする。

一括評価は、方針・期間・Scope・件数・費用・基準時刻と共有位置を保存し、明示したページごとに進める。Scopeの対象判定には保存した共有位置の階層を使う。各Issueの評価入力は、その要求を受け付けた現在版から固定し、一つのプロンプトへバックログ全体を渡さない。停止・費用不足・欠測では新たな要求を保留する。

新しいTriage設定の初期値は、入力1 MiB・出力4096 token・120秒・最大2試行・Workspace同時2評価。変更可能とし、既存の保存済み設定を初期値で上書きしない。

本人の追加判断により、Contextの入力組立て1回で読み込む固定版も初期10万件とする。選択と除外を合算し、同じ固定版の再利用は1件として次の取得前に判定する。配置数・出力byteとは別の上限であり、除外後の入力が小さい場合も保留になり得る。`KOUJOU_CONTEXT_MAX_LOADED`で変更でき、超過したTriageはモデルを呼ばず、採用済み値を保持する。全WorkspaceやContextの保存件数は制限しない。

## 割当と外部同期

Issueを明示的に関連付けたCLI Runは、採用値と依存先の完了を確認して通常の割当へ進む。同じ方針・尺度では優先度順、同順位は受付順とする。長期待機は経過時間を表示し、自動昇格しない。優先度を変更しただけでRunを作成・中断しない。通常の依存・検品・Runner能力・実行許可・処理枠の確認を維持する。

GitHub接続と優先度ラベルの対応は方針で設定し、既存の限定インストールの資格情報を使う。設定の変更には管理権限、外部反映には現在の対象の更新・実行許可も必要とする。ラベルへの送信は保存した採用値から行い、LLMを呼び直さない。

外部のイベントをページで取得し、Appの識別と保存した書込意図を照合する。ラベルの追加・削除だけを行い、無関係なラベルや本文・状態・非公開の理由・証拠は送信しない。応答が失われても先に観測し、保存した作用を照合してから再送する。外部の人の変更は固定として取り込み、内外の人の変更が競合した場合は保留を維持する。

実GitHubのラベルイベントでは`performed_via_github_app`がnullだったため、App自身のJWTで取得したApp ID・slugを確認し、そのslugのbotの数値IDをGitHubから取得してactorと照合する。人のactorや別Appを自身の書込みにしない。根拠は[認証したAppの取得](https://docs.github.com/en/rest/apps/apps#get-the-authenticated-app)と、公式Actionの[bot user IDの取得方法](https://github.com/actions/create-github-app-token#configure-git-cli-for-an-apps-bot-user)である。App情報がイベントにある場合は、そのIDを優先して照合する。

RESTのラベル操作には複数操作をまとめたCASがないため、観測と保存した意図を各作用に対応させる。同時編集を検知した後の書込みを止め、競合を利用者へ提示する。イベントの1ページは100件で、保存したページと既読イベントを使って継続する。

仕様の根拠はGitHub公式の[ラベルAPI](https://docs.github.com/en/rest/issues/labels)、[IssueイベントAPI](https://docs.github.com/en/rest/issues/events)、[イベントの種類](https://docs.github.com/en/rest/using-the-rest-api/issue-event-types)。API版は既存Connectorと同じ`2026-03-10`を使う。

## 認可と検証

GUI・HTTP・MCPは`internal/automation`の同じ保存・参照・版確認を使う。非公開の根拠は参照の依存関係から保護し、操作の参照だけで評価・発行・Run開始を追加しない。履歴・利用量・費用・採用元・同期を要求IDと固定参照で追えるようにする。

判定条件と現在の検証状況は[#28の計画](../progress/2026-10-18-issue-28-plan.md)を参照する。実provider・GitHubへの新たな書込み、共通画面、独立検品、CI、マージ後の照合を終えるまで完了としない。
